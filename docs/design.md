# 本地 Token 用量 Web 工具设计文档

版本：0.1
日期：2026-10-26（北京时间）
使用者：Sir
状态：设计稿，未开始 Web 开发

> 这份文档描述一个读取本机 Codex 会话日志、在浏览器中查询和查看 Token 用量的工具。现有命令行工具可以提供解析基础，但尚不具备本文设计的会话筛选、模型关联、推理强度分组、索引和网页功能。

## 1. 目标与边界

使用者可以选择一个精确到分钟的时间区间，按指定时区查询本地日志中的用量；从这个区间内实际产生用量的会话中选择一个、若干个或全部会话；按模型分别查看堆叠柱状图，并切换柱子的颜色含义。

本工具提供的是“现存本地日志可观察到的用量”，不承诺等于完整账户用量、官方用量页或账单。历史文件缺失、后台记录不完整、跨设备使用等情况要保留明确说明。它不会修改 ChatGPT 官方页面或原始日志。

### 2.1 顶部筛选区

- 起止输入支持日期选择和键盘输入，精度到分钟；跨日期时始终保留完整日期。
- 修改时间或时区后进入“待应用”状态。点击“应用时间范围”才更新会话候选与查询结果，避免用户改了一半日期就触发查询。
- 时区变化默认保留输入框中的当地日期和时分，并按新时区重新解释；应用前提示 UTC 偏移变化。这个行为属于建议默认值。
- 快捷范围按所选时区计算。“今天”从当地午夜开始，“昨天”到今天午夜结束；最近 7 天按滚动 7 个日历日的明确起止值展示，不隐藏实际日期。
- 分组粒度、会话选择、颜色模式和纵轴模式只作用于已应用的时间范围。
- 快捷范围只填写时间草稿，仍通过“应用时间范围”统一生效。

## 3. 时间与分桶规则

### 3.1 查询区间

例如输入：

- 开始：`2026-10-23 01:30`
- 结束：`2026-10-26 12:00`
- 时区：`Asia/Shanghai`

实际筛选为北京时间 `2026-10-23 01:30:00 ≤ 记录时间 < 2026-10-26 12:00:00`。

结束时间填 `12:00` 不包含 12:00 这一分钟。如需包含整个 12:00 分钟，填 `12:01`。界面在时间范围旁用简短说明明确这个规则。

后台将起止时间转换为 UTC 瞬间后筛选，原始事件时间始终以 UTC 保存。一个响应整体归属于它的 `token_usage_record.timestamp`，不按聊天创建时间归日，也不试图拆分响应在边界前后分别生成了多少 Token。

### 3.2 分组边界

| 粒度 | 所选时区内的自然分组边界 |
| --- | --- |
| 1 小时 | 每小时整点 |
| 6 小时 | 每日 00:00、06:00、12:00、18:00 |
| 12 小时 | 每日 00:00、12:00 |
| 天 | 当地当天 00:00 到次日 00:00 |

所有模型使用同一组分桶边界。实际计入范围为 `自然桶 ∩ 查询区间`。

上例在 6 小时粒度下，首桶实际统计 `10月23日 01:30～06:00`。在天粒度下，最后一天只统计 `10月26日 00:00～12:00`。首尾桶显示“部分时段”，悬浮提示使用实际统计起止时间。

日历日不能简单写成固定 24 小时；有夏令时的时区按日历边界计算。重复小时以 UTC 边界作为唯一标识，必要时在标签里附 UTC 偏移，不能把两个 01:00 合并。用户输入恰好落在跳时或重复分钟时，要求重新选择或用 UTC 指定，不默默猜测。

### 3.3 缩放与时间跨度

长时间范围下保留用户选择的粒度，通过横向缩放、拖动以及减少坐标标签密度解决拥挤；不静默改成更粗的统计粒度。视图缩放默认只改变可见窗口，不改变顶部全区间总量和强度占比。确需改变查询范围时仍通过时间输入应用。

超出合理渲染数量时明确提示并建议调整范围或粒度，不静默截断数据。具体上限在实现阶段通过实际数据验证。

## 4. 会话选择与筛选联动

### 4.1 候选集

会话候选由当前已应用的时间范围和“包含压缩调用”设置共同决定：至少存在一条满足这些条件、且 `total_tokens > 0` 的有效响应记录，才列为可选。

会话候选不能由会话创建日期决定，也不能仅因为整个会话的累计量大于零就加入。切换颜色模式、图表粒度或纵轴不会改变候选集。

每一项显示：

- 聊天标题；标题缺失时使用短 ID。
- 该会话在当前区间的 Token 合计。
- 必要时显示子会话或后台审核标记。
- 同名会话显示短 ID，避免选错。

默认按区间 Token 用量从高到低排列，提供名称搜索；“全选”明确指全部时间候选，不受搜索词限制。第一版不增加“全选搜索结果”这一额外行为。

### 4.2 两种选择状态

| 状态 | 含义 | 时间范围变化时 |
| --- | --- | --- |
| `all` | 始终选择当前候选全集 | 新范围内的候选全部生效 |
| `explicit` | 用户手选的 ID 集合，允许为空 | 保留与新候选集的交集，并提示移除了几个 |

`explicit + 空集合` 表示“没有选择会话”，绝不等价于全选。

“全选”切到 `all`；“清空”切到空的 `explicit`。从全选中取消某一项，转成包含其余当前候选的 `explicit`。重新加入全部当前候选不自动变为动态 `all`，避免换时间后无意纳入新会话。

用户自选会话全部失效时显示空选提示和重新选择入口，不自动选其他会话。

### 4.3 生效顺序

```text
有效且去重后的记录
  → 时间区间
  → 压缩调用口径
  → 会话候选全集
  → 当前会话选择
  → 模型划分
  → 时间分桶
  → 用量构成或推理强度分组
```

候选全集不能再受“当前会话选择”限制，否则取消一个会话后它会消失，无法重新勾选。

## 5. 模型图表与两种颜色模式

### 5.1 模型卡片

当前筛选结果中有正数用量的每个模型单独一张图。卡片包含模型名称、本模型全区间 Token 合计、图例、柱状图、时间坐标和悬浮提示。

模型按全区间用量从高到低排序；模型色彩含义在所有图中一致。后台审核的 `codex-auto-review` 保留原始标识，不擅自换成某个公开模型型号。无法归属的记录进入“未知模型”，仍计入总量。

界面中的模型是日志记载的配置归属，不宣称已验证服务端真实底层路由。

### 5.2 用量构成模式

正常完整记录使用三段堆叠，与参考图一致：

| 系列 | 计算 |
| --- | --- |
| 输入：命中缓存 | `cached_input_tokens` |
| 输入：未命中缓存 | `input_tokens - cached_input_tokens` |
| 输出 | `output_tokens` |

三段之和等于 `input_tokens + output_tokens`，也就是总 Token。缓存输入不能再次加到输入上；推理输出已经包含在输出中，不额外堆叠。

若少数记录缺少缓存分类，但输入和输出总量有效，保留总量，把该记录的输入放入额外的“输入：缓存状态未知”系列，不把未知当作未命中缓存。正常数据仍然只显示参考图中的三个系列。

`cache_write_input_tokens` 单独保留在索引；在未验证其与其他计数关系前，不再次加到总量或擅自改变缓存分类公式。

### 5.3 推理强度模式

同一模型、同一时间轴、同一根时间柱中，按实际出现的推理强度堆叠颜色。例如 `low`、`medium`、`high`；不为每种强度新增图表。

系列值为该时间桶、该模型、该强度下的 **总 Token**，不是仅计 `reasoning_output_tokens`。

模型图内部同时显示整个所选区间的强度占比：

`某强度占比 = 本模型该强度总 Token ÷ 本模型所选区间总 Token`

分母已经应用时间、会话和压缩调用条件，包含未知强度的用量。分组粒度变化和横向缩放不改变这个占比。百分比建议显示一位小数，精确值仍由未舍入计数计算；显示数值因四舍五入可能不恰好合计 100%。

- 图例显示各强度名称、区间 Token 和占比。
- 默认不在每根柱上标百分比。
- 悬浮柱子显示该时段各强度的具体 Token，以及本时段合计。
- 推理强度是日志记录的设置档位，不是实际思考时间，也不是输出中的推理比例。
- 不认识的新档位保留原名并分配稳定颜色；不丢弃、不自动映射到其他档位。
- 缺失强度使用“未知”。显式 `none` 与缺失不是一回事。

颜色映射对同一档位稳定，不因本次少了某个档位就整体换色；颜色以外仍提供文字标签和数值。未知系列用中性色。

### 5.4 模式、纵轴与悬浮

两种颜色模式共享完全相同的响应集合。因此同一模型同一时间柱的总高度和总量必须一致，仅内部颜色分组改变。

默认所有模型纵轴使用相同上限，适合比较绝对规模。“各模型独立缩放”仅改变各图纵轴范围，并在图中注明，不改变任何数值。

悬浮提示至少包含实际时间起止、总 Token、各系列值和响应次数。第一版图例只说明颜色，不通过点击隐藏系列，避免出现“总量是否重算”的额外歧义。支持键盘聚焦柱子查看同样的信息，提示框不能遮住关键控件或超出窗口。

## 6. 数据来源与归属规则

### 6.1 来源

| 来源 | 用途 | 访问方式 |
| --- | --- | --- |
| `~/.codex/sessions/**/*.jsonl` | 当前保留的会话事件与响应级用量 | 只读 |
| `~/.codex/archived_sessions/**/*.jsonl` | 已归档、仍保留文件的会话事件 | 只读 |
| `~/.codex/state_5.sqlite / threads` | 标题、项目关联、源路径、父子信息的补充与覆盖检查 | 只读，可缺失 |
| `state_5.sqlite / projects`、`thread_spawn_edges` | 项目名称和父子关系补充 | 只读，可缺失 |

标题索引不可用时不阻止用量查询。聊天累计量和历史项目数据库不作为响应级用量的第二份来源，防止重复计数。

已有调查确认存在日志原路径缺失，以及不同版本下字段差异。先前扫描数量只是当时的快照，界面不硬编码那些数量。

### 6.2 用量与会话

主要计数来源为顶层 `type = token_usage_record` 的 `payload.usage`。

- 以 `response_id` 去重，保留出现位置用于解释副本和冲突。
- 会话归属使用用量记录的 `thread_id`。
- `session_id`、`root_turn_id` 用于关系和溯源，不能代替 `thread_id`；子会话可能关联父会话的会话环境。
- 不累计 `turn_token_usage`、`thread_token_usage` 或旧 `token_count` 的累计快照。
- 不再次累计 `compacted.latest_token_usage_record` 和替代历史中的历史副本。

同一响应 ID 的相同副本只计一次。时间、用量或会话归属发生不可解释冲突时，将该响应整体隔离，不任选一份，也不把两份都计入；状态页显示被排除的响应数量和原因。

### 6.3 模型与强度关联

当前用量记录本身没有稳定的模型、推理强度字段，需要沿同一日志事件流关联该轮次的有效设置。

1. 用 `turn_id` 定位所属轮次，同时保留源文件与真实 `thread_id`，不把不同会话的上下文混在一起。
2. 模型主要取 `turn_context.model`，并核对显式设置事件中的模型信息。
3. 强度主要取 `turn_context.effort`；明确生效的设置事件可以更新后续响应的归属，例如 `configuration_update.reasoning.effort` 或对应轮次设置。
4. 按日志顺序或 `ordinal` 取响应之前最后一次适用的有效配置，不用“会话最后使用的模型/强度”反推全部历史。
5. 不用后出现的新配置覆盖已经发生的响应；找不到有效关联时标为未知。
6. 字段互相冲突而无法证明生效顺序时记录关联冲突，保留用量并归入对应维度的“未知”。

索引为模型和强度分别保留来源字段、来源事件位置与状态：`observed_config`、`unknown`、`conflict`。这表示配置归属依据，不是服务端实际执行模型的证明。未来日志格式变化通过版本适配器处理，不无条件信任同名字段。

### 6.4 上下文压缩

当前日志中可以观察到独立用量记录紧随 `compacted` 标记的压缩调用；识别为启发式规则，不承诺覆盖所有未来版本。

- 先用同一条用量记录后的结构化事件识别；存在可验证的 `compaction_response_id` 时也可核对同一响应。
- 保留 `true / false / unknown` 的压缩归属状态及来源。
- 默认包含全部有效用量；关闭开关时只排除确认识别的压缩调用，未知仍保留并在说明中注明。
- 压缩标记自身不是额外用量，不能再加一次。

## 7. 数据模型与查询接口

以下是实现建议，用于明确职责，不代表已经建立数据库或接口。

### 7.1 本地派生索引

| 实体 | 关键字段 |
| --- | --- |
| `source_files` | 路径、文件身份、大小、已处理字节位置、修改时间、解析版本、最后完整行位置、状态 |
| `usage_records` | `response_id`、UTC 时间、`thread_id`、`turn_id`、模型、强度、输入/缓存/输出/推理/总量、压缩状态、归属来源与状态 |
| `record_occurrences` | 响应 ID、源文件、序号/字节位置，用于去重、副本和变更追踪 |
| `turn_settings` | 所属源和会话范围、轮次、顺序、生效模型/强度及原始来源字段 |
| `conversations` | 会话 ID、标题、父会话、项目 ID、来源类型、标题来源 |
| `index_runs` | 索引版本、开始/完成时间、文件及记录数、错误/冲突/缺失计数 |

建议为时间、会话、模型和响应 ID 建立合适索引。所有统计依赖响应级记录，分桶结果不替代底层明细。

### 7.2 请求与返回

| 接口 | 职责 |
| --- | --- |
| `GET /api/v1/status` | 当前索引版本、更新时间、记录跨度、缺失/异常计数、是否正在刷新 |
| `POST /api/v1/session-options` | 根据时间与压缩口径返回可选会话及其区间用量 |
| `POST /api/v1/query` | 根据时间、会话、粒度返回总量、模型合计、两种分组与强度占比 |
| `POST /api/v1/index/refresh` | 触发派生索引更新，不修改原日志 |

会话 ID 等筛选值放在请求体中，不放入浏览器网址。第一版不提供远程分享链接。

查询请求示意，非真实记录：

```json
{
  "index_version": "snapshot-001",
  "timezone": "Asia/Shanghai",
  "start_local": "2026-10-23 01:30",
  "end_local": "2026-10-26 12:00",
  "granularity": "6h",
  "include_compaction": true,
  "sessions": { "mode": "all", "ids": [] }
}
```

`mode = all` 忽略 IDs；`mode = explicit` 且 IDs 为空时返回空选状态，不返回全量数据。`index_version` 必须与候选集一致；版本过期时提示重新取候选，而不是混用两个版本。

返回内容包括：

- 明确的区间、时区、粒度和索引版本。
- 已选会话数量、候选会话数量、整体用量与响应数。
- 每个模型的总量、所有时间桶、每桶用量构成与强度分类。
- 每模型的全区间强度用量和占比。
- 时间桶的自然边界、实际裁剪边界、部分桶标记、数据状态。
- 数据截止时间、来源覆盖说明、异常与未知归属计数。

前端不自行再实现一套不同的计数规则。总量、悬浮明细和强度占比都来自同一响应集合；颜色切换优先使用同一返回快照中的两套分组，避免切换时读到不同数据。

## 8. 索引刷新与界面一致性

### 8.1 初次和增量读取

首次扫描两个日志目录，建立响应级索引。之后按文件身份和已处理字节位置增量读取，扫描时固定每个文件的读取长度，只处理已写完整的记录。

- 末行未写完：保留进度，下一次接着读取，不当作完整记录。
- 文件变短、身份改变或已知前缀不一致：撤销该文件旧贡献并重读。
- 原文件消失：标记缺失；当前数据口径不把只剩缓存、已无任何现存源副本的记录继续算作已验证现存记录。更新后提示数据范围发生变化。
- 同一响应仍有其他有效源副本：保留一次有效贡献。
- 遇到坏行：隔离并累计错误，继续其他文件；不修复或覆盖源日志。

派生索引可以重建，但重建无法恢复原本就不存在的日志。完整重建只更换派生索引，不删除原始数据。

### 8.2 原子快照

刷新在新索引版本中完成并一次发布。刷新期间继续显示旧快照，同时显示“正在刷新”；不能让顶部总量、会话列表和图表分别来自不同版本。

用户快速修改筛选时，取消旧请求或忽略过期请求返回，避免旧结果覆盖新选择。刷新后在同一新快照中重新计算候选和当前选择，按第 4 节规则处理失效项。

本机服务只读取固定配置的日志目录及相关索引数据库；网页获取归一化统计和必要会话元信息，不传送聊天正文、内部指令、凭据或任意文件内容。

## 9. 状态、异常和覆盖说明

| 情况 | 页面行为 |
| --- | --- |
| 尚未建立索引 | 显示实际读取进度或阶段；不填模拟图表 |
| 正在刷新 | 保留上次结果并显示刷新状态 |
| 没有可选会话 | 提示当前范围未找到正数用量记录 |
| 用户清空选择 | 提示尚未选择会话，提供全选入口 |
| 单个时间桶无记录 | 保留时间位置、显示为空缺；悬浮说明“现存日志未找到记录” |
| 查询延伸到未来 | 未来部分淡化，显示实际数据截止时间 |
| 查询超出现存记录跨度 | 范围外部分标记为不可观察，不画成确认的账户零用量 |
| 部分源文件缺失 | 底部显示简短覆盖提示，展开查看计数与范围说明 |
| 未知模型/强度 | 独立系列或卡片，保留用量，说明归属缺失 |
| 格式异常或冲突记录 | 展示被排除数量及原因，不悄悄丢弃 |
| 标题索引不可读 | 使用会话短 ID，正常查询用量 |
| 查询或刷新失败 | 保留上次成功结果并标明未更新，提供重试 |
| 时间无效或顺序反转 | 在输入旁说明具体问题，不提交查询 |

空桶不生成“完整账户确实为零”的结论。接口应区分 `observed`、`no_records`、`future`、`outside_source_span` 等状态；不可观察状态绘制为空缺或淡化区域。跨桶求和只累加已观察到的数值，不能凭空补数据。

“最早记录至最新记录”只是现存记录跨度，不代表中间每个时段都完整。缺失原路径计数也不证明文件删除原因，不根据会话累计值分摊补齐。

## 10. 界面细节与可用性

- 所有模型图共用一套颜色模式与时间粒度，避免每张图含义不同。
- Tooltip 显示完整数值并用千位分隔；坐标轴可以用 K/M 等紧凑单位。
- 大量会话支持搜索及列表滚动；选择数量始终可见。
- 没有数据时不把“未知强度”画成 100%，只有实际正数分母才计算比例。
- 用户偏好只保存时区、粒度、颜色模式和纵轴模式；会话 ID 与聊天标题不写入网址。时间和会话选择是否跨次保存留待后续决定，第一版默认不保存。
- 主页面只呈现当前判断所需的覆盖提示；字段来源、去重、未知归属、压缩识别等说明放到可展开的统计说明中。

## 11. 验收标准

所有验收以人工构造的已知数据和同一快照的本地真实记录交叉核对。不能只凭图表看起来正常就通过。

| 编号 | 验收场景 | 预期 |
| --- | --- | --- |
| T01 | 起点前、恰好起点、终点前、恰好终点各一条记录 | 只计起点及终点之前的匹配记录 |
| T02 | 同一 UTC 记录在北京时间跨日 | 正确归入当地日期 |
| T03 | 非整点起止，分别切 1h/6h/12h/day | 首尾裁剪准确，四种粒度合计一致 |
| T04 | 夏令时重复小时和非 24 小时日 | 瞬间不重不漏，重复小时可区分 |
| T05 | 夏令时不存在或重复的用户输入分钟 | 明确拒绝歧义，不猜测 |
| T06 | 会话创建很早，但区间内有消耗 | 可以选择 |
| T07 | 会话累计量大于零，但区间内没有消耗 | 不可选择 |
| T08 | 全选后改变时间范围 | 自动覆盖新候选全集 |
| T09 | 自选后改变时间范围 | 只保留交集；全部失效时空选，不变全选 |
| T10 | 清空会话 | 返回空选结果，不返回所有数据 |
| T11 | 搜索会话名称 | 不改变已有选择，“全选”仍指全部时间候选 |
| T12 | 同名会话与没有标题的会话 | 短 ID 可以区分和选择 |
| T13 | 同会话在不同轮次使用不同模型或强度 | 分别归属，不按最后配置覆盖历史 |
| T14 | 同轮次发生显式配置更新 | 仅影响更新后适用的响应；不确定时归未知 |
| T15 | 缺失模型/强度或配置冲突 | 用量保留，显示未知，不乱填档位 |
| T16 | 显式 none 与缺失强度同时出现 | 分成两个类别 |
| T17 | 用量构成切到推理强度 | 每模型每桶总量、整体总量均保持一致 |
| T18 | 推理强度占比 | 分母包含同模型全区间全部选定用量，未舍入值合计为 100% |
| T19 | 切换分组粒度或图表缩放 | 全区间强度占比不变 |
| T20 | 切换时间、会话或压缩口径 | 占比按同一新响应集合重算 |
| T21 | 缓存输入与推理输出 | 不重复加到总量；缓存分类缺失时不猜成零 |
| T22 | 同一响应出现在多个文件或压缩历史里 | 只计一次 |
| T23 | 同响应 ID 存在不可解释冲突 | 隔离整条响应并显示异常数 |
| T24 | 关闭压缩调用开关 | 排除已确认压缩用量，同时重算候选、总量、图表、占比 |
| T25 | 空桶、未来和日志跨度外区间 | 不把缺失画成已确认零用量 |
| T26 | 正在追加的末行、坏行、被截断/替换/移除文件 | 不崩溃，不重复累计；源变化与跳过项可观察 |
| T27 | 刷新与筛选请求并发 | 候选、总量和图表来自同一索引版本；过期请求不覆盖新结果 |
| T28 | 正常和窄窗口实际浏览器检查 | 柱体、标签、颜色、tooltip、滚动、键盘操作和空状态可用 |
| T29 | 各模型合计、各桶合计、各系列合计 | 均与相同过滤条件下的响应级总量核对一致 |
| T30 | 第一版的读取和刷新 | 不修改原始日志、官方数据库或现有应用配置 |

## 12. 建议实现顺序与待定项

### 12.1 实现顺序（计划，不是已完成工作）

1. 从现有命令行代码抽出解析与用量验证，补齐模型、强度、真实会话归属和压缩状态。
2. 建立可追踪副本的本地索引，完成边界、去重、配置变化与增量读取测试。
3. 实现同版本的候选与查询接口，先用固定测试数据验证筛选和合计。
4. 完成参考样式的页面、两种图表模式与联动状态。
5. 在实际浏览器中核对真实数据、窗口尺寸、悬浮明细、筛选和刷新，并交付本地启动方式。

### 12.2 可以继续调整但不阻塞设计阅读的事项

- 首次打开显示当天、最近 7 天还是上次范围。
- 是否将子会话与父会话分层展示；第一版建议独立可选，不隐式递归选中。
- 是否默认隐藏后台审核模型；第一版建议不隐藏，避免总量悄悄减少。
- 之后是否增加响应次数占比、项目筛选、明细导出和自动刷新；不并入第一版必需范围。
- 前端图表组件与本地 HTTP 服务的具体库在实现前选定；不影响本文数据口径。使用时核对其当时的文档和本机依赖。
